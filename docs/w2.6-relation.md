# W2.6: the relation has to travel

A working note, written before the code so the next session starts with the
decision instead of the discovery. W2.6 is "absolute value and inequalities with a
sign chart over the exact critical points". The mathematics is not the problem:
`Solutions::Inequality { var, intervals }` already holds a union of intervals and
already renders `(-1, 3]` and `… \cup …`. The problem is that **the relation is
destroyed before the solver is asked**.

## The defect

The pipeline builds `left − right` for every line:

- `canlab-input` reads `|x−1| < 2` into a relation node;
- the GUI's `build_equations` turns each line into `(left, Option<right>)` and
  then `add([left, mul([-1, right])])`;
- `Solver::solve_all(eq, var)` receives a *difference* and a variable.

So `|x−1| < 2`, `|x−1| > 2` and `|x−1| = 2` arrive as the same expression, and no
function of that expression can recover which was typed. Any implementation of
inequalities that works on the difference is guessing — which is exactly the
mistake the corpus format refuses for rows.

## The shape of the fix

1. **A relation value**, in `canlab-core` (it is syntax, not solving):
   ```rust
   pub enum Comparator { Less, LessOrEqual, Greater, GreaterOrEqual }
   pub struct Relation { pub left: Expr, pub right: Expr, pub comparator: Comparator }
   ```
2. **One new trait method**, defaulting to a refusal so no backend silently
   degrades:
   ```rust
   fn solve_relation(&self, relation: &Relation, var: SymbolId) -> Result<Solutions, SolverError> {
       Err(SolverError::NotImplemented)
   }
   ```
   `solve_all` keeps its signature: an equation is a *relation with both sides
   known to be equal*, and nothing about the existing callers changes.
3. **The job carries what was typed.** `JobOp::SolveRelation(Relation, SymbolId)`
   beside the existing `Solve`, and `build_equations` keeps the comparator it
   currently drops. The GUI's result card needs no change: a `Solutions` is a
   `Solutions` whether it came from `=` or `<`.
4. **The method itself**, in `canlab-solver`: move everything to one side, find the
   exact critical points (roots of the numerator, roots of the denominator made
   visible by the same rational-root and quadratic machinery W2.3 built), split
   the line into intervals, test one interior point per interval numerically, and
   report the intervals where the sign matches the comparator. Endpoint openness
   follows from the comparator and from whether the point is a root of the
   denominator.

The sign chart is a *numerical* test of a small set of *exact* candidates. That is
the same division of labour as the tracer: exact where it decides, numeric where it
samples — and it is why a wrong answer would show up as a wrong interval boundary,
which the corpus rows can pin.

## What this unlocks

- `|x−1| < 2` → `(-1, 3)`, `(x−1)/(x+2) ≥ 0` → `(-∞, -2) ∪ [1, ∞)`.
- The `Inequality` arm of the result panel, which is written and has never been
  shown a real answer.
- The same relation value is what a future "solve for `y`" on an inequality needs,
  so this is not a one-off.

## The test that must exist before the feature

`|x−1| < 2` **and** `|x−1| > 2` **and** `|x−1| = 2` in one test file: the first two
differ only in the comparator, so they are the pair that proves the comparator
survives the trip. A suite that only tests `<` would pass on an implementation that
hard-codes "less than".
